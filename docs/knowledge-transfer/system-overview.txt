4. ARCHITECTURE
---------------
Backend
  Modular monolith, one deployable. Minimal-API endpoints -> application service
  -> pure domain rules -> PostgreSQL via Npgsql (raw SQL in a transaction).
  EF Core is used only for ASP.NET Identity. No mediator, no generic repository,
  no event sourcing. Add abstractions only when a second use needs them.

Frontend
  Single-page React app served as static files by the API in production-like
  runs; Vite dev server proxies /api in development. No router/state library.
  All server calls go through api.ts. The UI shows an "estimated total" but the
  server recomputes and returns the authoritative total.

Database (PostgreSQL, schemas)
  public       schema_migrations (applied migrations + checksums)
  core         tenant, tenant_membership, business_profile, branch,
			   stock_location
  catalog      category, product
  inventory    opening_stock_document, opening_stock_line, stock_movement,
			   stock_balance, item_cost
  accounting   account, journal_entry, journal_line
  audit        audit_event
  platform     idempotency_record
  security     security_event
  (Identity tables for users live via EF Core migration 001.)

Roles
  Migrator role: owns objects, runs migrations (tests only use it for setup).
  rbos_app: the runtime role. Not superuser, no BYPASSRLS, owns no tables. The
  API refuses to start if current_user is not rbos_app.

Tenant isolation
  Every business table carries tenant_id. TenantDb.BeginAsync sets two
  transaction-local settings (app.user_id, app.tenant_id). Never pass tenant id
  from the client as authority: tenant is derived from the signed-in user's
  active membership.

RLS (row-level security)
  Enabled AND FORCED on tenant tables (004, 005). Policies compare tenant_id to
  app.tenant_id and membership to app.user_id. Integration tests prove a second
  tenant sees nothing and cannot write to the first.

Authentication
  ASP.NET Core Identity (GUID users). Password min length 12, lockout after 5
  failures for 10 minutes, cookie rbos.auth (HttpOnly, SameSite=Strict, Secure
  outside Development, 8 h). Fallback authorization policy requires an
  authenticated user; only csrf, register, login, healthz are anonymous.
  Registration is closed by default once any user exists
  (Rbos:AllowOpenRegistration=true opens it; tests and e2e set it).
  CSRF: antiforgery token from GET /api/csrf sent as X-CSRF-TOKEN on every
  non-GET /api call.

Idempotency
  Mutations send an Idempotency-Key header (8-100 chars). Stored in
  platform.idempotency_record with a hash of the normalised command. Same key and
  same content -> original result returned (replayed=true), nothing re-posted.
  Same key, different content -> conflict. Unique constraints are the final
  guard under concurrency. Bootstrap is also idempotent per user.
  A second opening-stock posting for the same location is blocked (conflict).

Posting transaction (opening stock)
  One transaction: audit event, document, lines, stock movement, balance,
  item cost (WAC), journal entry + two lines, idempotency record. All or nothing.


5. DOMAIN MODEL
---------------
  tenant                 A business (isolation boundary). Created at bootstrap.
  tenant_membership      Links user to tenant with role (Owner) and status.
  business_profile       Display name; GST profile deliberately "not yet known".
  branch                 A shop/branch under the tenant.
  stock_location         Where stock is held (belongs to a branch).
  category, product      Catalogue. Product has internal SKU, unit (pcs/set/pack/m),
						 generic flag; branded products have brand and model.
						 Tax data on products is unverified metadata.
  opening_stock_document One-time document establishing starting stock for a
						 location. Lines: product, quantity, unit cost.
  stock_movement         Immutable record of quantity change (source of truth).
  stock_balance          Projection: current quantity per product/location.
  item_cost              Weighted average cost per product (known-cost receipts
						 only in Slice 1).
  account                Chart accounts seeded at bootstrap: 1400 Inventory,
						 3900 Opening Balance Equity.
  journal_entry/line     Balanced double-entry record of the opening value
						 (debit Inventory, credit Opening Balance Equity).
  audit_event            Who did what, when, within the tenant.
  idempotency_record     Remembers completed commands (see section 4).
  security_event         Security-relevant events table (schema present).

Relationships in short: tenant 1-* branch 1-* stock_location; tenant 1-*
product; opening_stock_document 1-* lines -> product; each document produces
movements, balance, cost and one balanced journal entry.

Why: movements are facts, balances/costs are projections, the journal makes
inventory value auditable, and tenant_id everywhere makes RLS enforceable.
Money/quantity rules: money 2 dp round half away from zero; quantity 3 dp;
unit cost 4 dp; negative quantity, zero or unknown cost are rejected.


6. IMPLEMENTED WORKFLOWS (API routes under /api)
------------------------------------------------
  Tenant bootstrap   POST /bootstrap (needs Idempotency-Key). Creates tenant,
					 Owner membership, business profile, branch, stock location,
					 and the two accounts in one transaction. Repeat returns the
					 existing tenant (replayed=true). GET /me shows tenant id.
  Product creation   POST /products (name, categoryName, baseUnit, isGeneric,
					 brand, model). Branded product requires brand/model; SKU is
					 generated. GET /products lists the tenant's products.
  Generic product    Same endpoint with isGeneric=true and no brand/model (for
					 unbranded items such as plain adapters).
  Opening stock      POST /opening-stock (locationId, effectiveDate, lines of
					 productId/quantity/unitCost; Idempotency-Key required).
					 Server validates, recomputes the total, posts everything
					 atomically. Outcomes: posted, replayed, conflict, invalid.
  Current stock      GET /stock returns product, location, quantity, WAC and
					 value. GET /locations lists stock locations.
  Auth support       POST /auth/register, /auth/login, /auth/logout, GET /csrf,
					 GET /healthz.
  Not in the UI: stock movement history (data exists, no screen).

8. SECURITY
-----------
Current protections
  - Forced RLS, separate migrator and runtime roles, runtime role assertion.
  - Tenant derived server-side; cross-tenant access tested.
  - Identity with 12-char minimum, lockout, HttpOnly/SameSite=Strict cookies,
	Secure outside Development, CSRF tokens on all mutations.
  - Security headers (CSP, nosniff, DENY framing, no-referrer, Permissions-
	Policy), no-store on API, 64 KB mutation limit, JSON-only mutations.
  - Generic login and duplicate-registration responses.
  - Generic 500 handler (no stack traces to clients).
  - Registration closed by default; secrets only in user secrets; migration
	checksum protection; idempotency and atomic posting.
Remaining limitations (see docs/quality/slice-1-1-review.md)
  - No rate limiting (Medium). Login timing may reveal account existence
	(Medium). First-registration race (Low). Password policy is length only.
  - AllowOpenRegistration is a plain flag; consider failing startup if enabled
	outside Development.
  - HTTPS/HSTS behaviour only reasoned about, not exercised.
  - Only the Owner role exists; authorization matrix is not fully implemented.
  - Review was self-review; not an independent audit or penetration test.
