# ADR-025 and ADR-026: Flexible sales, provisional negative-stock cost and document capture

## ADR-025 — Physical negative stock with provisional cost and later reconciliation

**Status:** Implemented on branch `feat/flexible-sales-handwritten-invoice` in PR #64; migration and exact-head CI are still pending. Not merged or deployed.
**Context:** Shopkeepers sometimes sell goods before the system has recorded the receipt, or have a location-level stock deficit. A physical stock prohibition blocks a real sale; simply deleting the check creates unbounded valuation errors. Current stock is location-scoped while WAC is product-wide.
**Decision:** Permit physical location quantity to become negative, but never allow product-wide valued inventory quantity/value to become negative. For the unvalued short quantity, use the current positive WAC; if it is unavailable, use the most recent positive unit cost on an incoming inventory movement. If neither exists, reject posting and require a cost-bearing receipt/opening adjustment first. Persist provisional quantity/cost against the exact sale line. Later receipts at the same location allocate FIFO by commitment creation time and ID, debit the clearing liability, credit inventory at actual landed cost and post the actual-versus-provisional difference to COGS. No tenant-wide cross-location allocation. Do not use zero cost, rewrite sale price/quantity history or treat negative physical quantity as a negative inventory asset.
**Alternatives:** Reject the sale (current behaviour); remove stock validation and allow negative WAC; post zero-cost sales and adjust later; create a payable/stock receipt automatically (rejected: the system cannot invent a purchase).
**Benefits:** Captures genuine shop activity while preserving an explainable audit trail. **Costs:** Additional allocation ledger, journal rules, reconciliation and operational alerts.
**Risks:** Wrong fallback estimate, cross-location allocation ambiguity, date/period-lock interactions and misleading gross margin until adjustment. **Reversibility:** Medium.
**Consequences:** Migration 056 adds an RLS-protected commitment subledger and account 1410 `Negative Stock Clearing`. Returns first reverse outstanding provisional quantity/cost; receipt settlements update the cost projections and post a linked adjustment journal; cancellation reverses the current inventory/clearing split and closes outstanding commitments. The selected fallback and FIFO same-location policy are implemented on the PR branch; owner/CA review remains a production-release control.
**Required validation:** Zero/partial stock sale → receipt settlement → return/cancellation; valued inventory remains non-negative; clearing account reconciles to open commitments; multi-location isolation and concurrent posting. **PO decision needed:** Implementation policy selected; final owner review before production. **Professional review:** CA review before production release.

## ADR-026 — Handwritten sales invoice capture as an unposted draft

**Status:** Backend extraction and Generate Invoice review UI implemented on PR #64 branch; not merged/deployed. AI Gateway explicitly excluded.
**Context:** Shopkeepers receive handwritten customer invoices and need to record the sale without retyping every line. Existing supplier invoice extraction is a different workflow and explicitly ignores handwriting.
**Decision proposal:** Add a separate sales-document extraction contract that uses the exact `ItemTagCaptureService` image-extraction path: `ItemTagGeminiModels`, direct Gemini model attempts, optional Groq only when `Groq:ItemTagFallbackEnabled` is enabled, `VisionProviderFallback`, 900 ms local OCR fast path, SkiaSharp image preparation and the existing item-tag attempt/total provider budgets, strict file validation and safe metadata-only logs. Do not call `AiGateway`, create an AI Gateway usage-ledger entry, or add provider credentials/configuration. Extraction returns an editable draft with confidence/warnings. The current implementation processes the photo in memory and does not retain it; source invoice number/date are shown separately from RBOS numbering. Human review and confirmation are required. The accepted draft is posted only through the existing sales posting service. AI has no posting authority and cannot decide authoritative tax, totals, inventory, cost or accounting.
**Alternatives:** Tesseract-only handwriting (rejected as primary; designed for printed text); a separate AI posting pipeline (rejected); automatic posting (rejected).
**Benefits:** Less manual entry without bypassing controls. **Costs:** Provider budget, review UX and test corpus. Follow the existing image-upload evidence-retention policy; do not add a separate storage path without a demonstrated requirement.
**Risks:** Misread model numbers, quantities, handwritten totals, customer/seller confusion and prompt injection in uploaded documents. **Reversibility:** High.
**Consequences:** Unknown values remain null; source invoice number/date are references, not RBOS legal numbering. Low-confidence data is shown for review. The image is not persisted by this slice. No extracted draft writes sale, stock, journal or balance records.
**Required validation:** Synthetic handwritten corpus, field-level correction workflow, extraction failure and prompt-injection tests, tenant isolation, zero-posting extraction guarantee. **PO decision needed:** Yes. **Professional review:** Tax/accounting rules remain subject to CA review.
