# Normalisation and lexicon spec (L0 / L1 / L2), v1.1

Supersedes the Step 1 draft `normalisation.md`, which was removed. That draft's hand-written variant table was **withdrawn** because:
- it came from the author's own knowledge rather than from the anchors;
- one of its variants (`lauta`) appears in test item t019.

## 0. Shared pipeline (identical for A, C1 and C2)

```
raw text
  → guard (G)                        same code for every resolver
  → prep(level) → prepared string    same string for every resolver
  → resolver(A | C1 | C2)            only this step differs
  → decision(tau, delta)             same rule; tau/delta tuned per resolver × level
```

- The resolvers never see the raw text.
- `prepared/<level>/{anchors,tuning,test}.jsonl` are written once, hashed and logged in `environment.json`.

## 1. Guard G (all resolvers)
Rejects the input before scoring if, after NFC, it:
- is empty;
- contains `://`, `javascript:` or `data:`;
- contains `#/` followed by an id that is not in `destinations.v1.json`;
- contains a digit sequence.

The guard is fixed now, without looking at the test file. Its hit rate is reported separately, so guard wins are not credited to any model.

## 2. L0: basic
NFC → lowercase (Latin) → replace every character that is not a letter, combining mark, digit or space with a space → collapse whitespace → trim.

## 3. L1: rule-based transliteration (no hand-picked word lists)
1. **Devanagari → Latin.** A fixed character-level scheme (ISO-15919 simplified to ASCII):
   - drop the inherent schwa at the end of a word;
   - `ं`/`ँ` → `n`;
   - nukta forms → base consonant.
2. **Latin key folding.** The same function runs on every Latin token, whether original or transliterated:
   - collapse doubled letters: `aa→a`, `ee→i`, `oo→u`;
   - `w→v`, `z→j`, `ph→f`;
   - drop a final `h` after a vowel;
   - `q→k`, `ck→k`.

   `udhaar`, `udhar` and `उधार` all become `udhar`.
3. The rules are pure code, written before stage 4. Their source hash goes into `MANIFEST.sha256`.

## 4. L2: lexicon built only from anchors

`lexicon.v1.json` is **generated by a script**, never hand-edited. The script's only inputs are `destinations.v1.json` and `data/anchors.v1.json`.

**Generation algorithm** (deterministic, no model):
1. Apply L1 to all 200 anchors and tokenise.
2. For each folded token, record the set of destinations whose anchors contain it.
3. **Tag = page prefix** (`sell`, `buy`, `stock`, `parties`, `money`, `more`, `home`, `settings`). A token gets the tag `@<prefix>` only if it appears in anchors of exactly one prefix. Tokens shared across prefixes (`return`, `wapas`, `bill`, `history`) get no tag, so genuine ambiguity is kept.
4. **Synonym classes:**
   - tokens are synonyms when they fill the same slot of an otherwise identical anchor template (for example `X karo` vs `X kholo`) in at least 2 destinations;
   - each class maps to its alphabetically first member.
5. Output `{version, sourceHashes:{destinations, anchors}, tokens:{key:{tags,classRep}}}`. The file is frozen and its hash added to the manifest.

**Leakage proof:**
- The generator opens two files only.
- The run script checks `lexicon.sourceHashes` against the manifest and aborts on any mismatch.
- To change the lexicon, change the algorithm or the anchors, which produces a new version.

**L2 transform (identical for all resolvers and for the anchors):**
1. Replace each token with its class representative.
2. Append the sorted, unique tags as tokens.

   Example: `kharcha entry karo` → `kharcha entri karo @money`.

A matches the tag tokens like any other token. C embeds the string as it is.

## 5. Known consequences
- Words that are not in any anchor (`kiraya`, `bijli`, `kist`) get no help from L1/L2. That is intended.
- Folding can merge unrelated words (`mal` could be "goods" or "mall"). The collision count is reported in `environment.json`.
